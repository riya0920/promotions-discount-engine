==============================================================================
SE-2 POSTGRES PASS -- A PREDICTION THIS PROJECT MADE, TESTED
==============================================================================
The claim: 'redemptions of DIFFERENT promotions queue here and would
proceed in parallel on Postgres. The shape transfers; the throughput
number does not.'

It has two halves and they were never equally safe. 'The shape
transfers' is a statement about the conditional UPDATE and is true
anywhere -- the check and the decrement are one statement. 'Different
promotions would proceed in parallel' is an assertion about another
engine's lock granularity, made without one.

==============================================================================
A. THE CAP HOLDS UNDER REAL ROW-LEVEL CONCURRENCY
==============================================================================
  engine  promos  granted  refused  consumed  overspend  n_errors
postgres       1      100      540       100          0         0
  sqlite       1      100      540       100          0         0
postgres       8      400      240       400          0         0
  sqlite       8      400      240       400          0         0

  Overspend on both engines, every configuration: 0. The cap is
  unbreachable because `remaining > 0` lives in the WHERE clause, so
  the check and the decrement cannot be separated by a scheduler.
  THAT HALF OF THE PREDICTION WAS RIGHT, and it is the half that
  matters for correctness.

==============================================================================
B. DO DIFFERENT PROMOTIONS ACTUALLY PROCEED IN PARALLEL?
==============================================================================
Same workload, one promotion versus sixteen. Paired inside each
repetition so machine drift cancels rather than landing in the ratio.

  sqlite    median 1.00x  range 0.46-1.30  |  above 1.0 in  8/15, sign p = 1.0000
  postgres  median 1.18x  range 0.94-1.58  |  above 1.0 in 13/15, sign p = 0.0074

  THE PREDICTION HOLDS. Spreading the same redemption storm across
  sixteen promotions speeds Postgres up (p = 0.007) and does nothing
  measurable to SQLite (p = 1.000), which is exactly what a global
  write lock versus row locks predicts.

  THE STATISTIC HAD TO BE CHOSEN CAREFULLY AND THE OBVIOUS ONE IS
  WRONG HERE. Testing Postgres against SQLite pairwise reads p = 0.30
  and looks like a null result. It is not -- it is SQLite's noise
  swamping a real effect: its ratio ranges 0.46 to 1.30 because its
  runs finish in a fraction of a second and timing jitter is
  proportionally enormous. Testing each engine against 1.0 separately
  is the question that was actually being asked.

  AND THE SIZE IS SMALLER THAN THE PHRASE SUGGESTS. 'Proceed in
  parallel' implies the sixteen-promotion case should be many times
  faster; measured, it is 1.18x. At 16 workers the bottleneck is
  already partly the client, and no engine change moves that.

  Note also what is NOT here: the budget cap has no retry loop, so a
  losing writer waits on a row lock and then succeeds. SE-1's
  optimistic reservation DOES retry, and on the same engine it starves
  52%% of requests on a hot row. Same database, same kind of
  contention, opposite outcome -- the difference is the retry loop, not
  the engine.
